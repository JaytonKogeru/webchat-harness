# Launchers

These launchers are intentionally short. The universal behavior lives in [`HARNESS.md`](HARNESS.md); the target repository's local objective/map lives in its root `WEBCHAT.md` created with [`BOOTSTRAP.md`](BOOTSTRAP.md).

## Full-project ownership run

Replace `<owner/repo>` with the target repository.

```text
Take full ownership of <owner/repo> for this run.

First load and follow the current canonical HARNESS.md from JaytonKogeru/webchat-harness. Then read <owner/repo>/WEBCHAT.md and the target repository's own authoritative instructions/state that it references.

Use WEBCHAT.md to anchor the project's actual objective, meaningful progress, project truths, source-of-truth map, verification surfaces, and authority boundaries. It is an objective/map, not a task queue or frozen specification.

Use the native GitHub tools directly. Reconstruct the live state, audit from first principles, choose the highest-value resolvable gap relative to the real project objective, act on it, verify the result with evidence actually available, adversarially review your work, then re-audit from the new repository state and continue under the harness terminal conditions.

Do not stop at planning, an audit, a work packet, a commit, a pull request, passing one check, or partial success. Do not ask me questions that you can resolve from the repository, tools, evidence, or external research. Do not switch this task to Work or Codex unless I explicitly ask you to.

Do not give me a running diary. Start now.
```

If `WEBCHAT.md` does not exist, bootstrap the target repository first using [`BOOTSTRAP.md`](BOOTSTRAP.md) rather than making a large autonomous run infer project identity from scratch.

## Resume an existing ownership run

```text
Resume autonomous ownership of <owner/repo> under the current canonical HARNESS.md from JaytonKogeru/webchat-harness.

Reload <owner/repo>/WEBCHAT.md, then reconstruct reality from the live repository, recent relevant commits/branches/PRs, authoritative project files, and available external evidence. Do not trust the previous chat's narrative or old task queue as current state.

Determine what was actually completed, what remains materially important relative to the project objective, and which earlier plans are now stale. Continue the audit → act → verify → adversarial review → re-audit loop until the harness terminal condition is genuinely met or a real non-delegable blocker remains.

Stay in standard Web Chat and use the native GitHub tools directly. Do not give me a running diary.
```

## Independent adversarial review

Prefer a fresh chat so the reviewer is not anchored to the builder's narrative.

```text
Review <owner/repo> independently under the current canonical HARNESS.md from JaytonKogeru/webchat-harness.

Read <owner/repo>/WEBCHAT.md first to anchor the real project objective and local truths. Assume another agent claims the current delivery is complete. Do not trust that claim, its plan, or its self-review.

Reconstruct the live state from repository evidence, try to falsify the completion claim, and directly fix every material problem that can be resolved within the available authority. Re-audit after fixes and stop only under the harness terminal conditions.
```

## What not to put in the launcher

Do not turn the launch message into a second workflow manual. Avoid mandatory brainstorming gates, human approval of every design, universal TDD, fixed PR counts, fixed agent roles, or a mandatory PRD pipeline unless the target project itself genuinely requires them.
